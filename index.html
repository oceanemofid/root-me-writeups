01
HTML - Code source
5 pts · secret exposé en commentaire HTML
▾

Objectif

Contourner l'authentification d'une page de connexion sans connaître le mot de passe à l'avance.

Vulnérabilité

Le mot de passe était laissé en clair dans un commentaire HTML (<!-- ... -->) — invisible à l'écran mais lisible dans le code source.

Exploitation

Affichage du code source (Ctrl+U) → repérage du commentaire → mot de passe réutilisé dans le formulaire.

Remédiation

Ne jamais laisser de secret dans le HTML livré au client, pas même en commentaire.

02
HTTP - User-agent
10 pts · contrôle d'accès basé sur un header client
▾

Objectif

Devenir « admin » aux yeux de l'application pour obtenir le mot de passe de validation.

Vulnérabilité

L'accès dépend du header HTTP User-Agent, entièrement fourni par le client et falsifiable à volonté.

Exploitation

Modification du User-Agent dans les DevTools pour correspondre au navigateur « admin » attendu, puis rechargement de la page.

Remédiation

Ne jamais baser une autorisation sur un header non vérifié ; utiliser une vraie session serveur.

04
HTTP - POST (RandGame)
15 pts · validation uniquement côté client
▾

Objectif

Obtenir un score élevé alors que le jeu ne permet normalement qu'un score aléatoire limité.

Vulnérabilité

Le score est vérifié uniquement côté client ; le serveur fait confiance à la valeur POST reçue, sans la recalculer.

Exploitation

Éditer le DOM manuellement ne suffit pas de façon fiable. Solution via la Console :

document.forms[0].score.value = 9999;
document.forms[0].onsubmit = null;
document.forms[0].submit();

Remédiation

Toujours revalider côté serveur toute donnée métier critique, même calculée côté client.

Vulnérabilité

06
HTTP - Headers
15 pts · contrôle d'accès basé sur un header custom
▾

Objectif

Accéder à une fonctionnalité réservée à l'administrateur, contrôlée par un header HTTP personnalisé.

Vulnérabilité

Contrôle d'accès basé sur un header arbitraire (Header-Rootme-Admin) envoyé par le client.

Exploitation

« Edit and Resend » du Network s'est révélé peu fiable pour un header custom. Solution via fetch() en Console :

fetch(location.href, { headers: { "Header-Rootme-Admin": "1" } })
  .then(r => r.text()).then(console.log);

Remédiation

Ne jamais utiliser un header client comme preuve d'autorisation.

10
SQL injection - String
30 pts · injection UNION-based (SQLite)
▾

Objectif

Extraire les identifiants admin stockés en base via une injection UNION.

Vulnérabilité

Entrée du champ Recherche insérée directement dans la requête SQL (contexte chaîne), backend SQLite3.

Exploitation

1. Confirmation : une quote casse la requête.
2. Colonnes : ' UNION SELECT NULL, NULL-- - → 2 colonnes.
3. Schéma : ' UNION SELECT name, sql FROM sqlite_master WHERE type='table'-- - → table users.
4. Extraction : ' UNION SELECT username, password FROM users-- -

Remédiation

Requêtes préparées partout, y compris pour une fonctionnalité de recherche. Ne pas afficher les erreurs SQL détaillées en prod.

11
JWT - Introduction
20 pts · JWT forgé avec alg: none
▾

Objectif

Obtenir un accès admin en forgeant un JWT sans connaître la clé de signature.

Vulnérabilité

Le serveur accepte l'algorithme none : un JWT sans signature reste accepté si l'entête l'annonce.

Exploitation

Via jwt_tool : header alg → none, payload username → admin, signature retirée (« Strip signature using none algorithm »). Le jeton forgé remplace le cookie jwt dans Burp Suite.

Remédiation

Rejeter explicitement alg: none et whitelister les algorithmes acceptés côté serveur.
